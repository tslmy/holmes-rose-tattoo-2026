Linear <-> review queue sync

Rendered from docs/linear-review-sync.md, a working record of the project.

review/queue.json stays the source of truth the runner reads. Linear is where the user reviews asynchronously. Every item with status pending has one Linear issue in project "Rose Tattoo remaster":

  • Title <item-id>: <queue title> (the id before the first colon is the link to the queue item).
  • Label Needs approval, assignee the user, status Todo.
  • Description: queue number, the provisional default in use, the options, a pointer to review/queue.md and any docs/ results file. No game-derived images or extracted text.

Who wrote a comment

Agents and the user share one Linear account, so the author field cannot tell them apart. Every agent comment must start with 🤖. (Older agent comments starting "Settled." count as agent comments.) Anything else on a Needs approval issue is the user.

Automation without AI

uv run remaster linear-sync [--dry-run] (tools/remaster/linear_sync.py) applies the Linear -> queue rules below with a plain Python poll, needs no model, and shows a macOS notification per decision. It does not message sessions: the decision is in queue.json, and overturned items re-queue their tagged jobs, so the runner picks it up. It does not create issues (queue -> Linear stays with sessions). Setup: create a personal API key in Linear (Settings > Security & access), store it with security add-generic-password -s remaster-linear -a $USER -w, then uv run remaster linear-sync launchd > ~/Library/LaunchAgents/local.shcrt.remaster-linear-sync.plist and launchctl load it (every 5 minutes).

Linear -> queue rules

For each Needs approval issue whose queue item is still pending, in order:

  1. User comment (no 🤖 prefix) newer than work/linear-sync-state.json seen_comments:
    • starts with a confirm word (keep, yes, ok, default, approve, accept): uv run remaster review decide <id> "<comment>"
    • starts with decide: or choose:: decide with the text after the colon (this overturns the default unless it confirms it, same rule as the CLI)
    • anything else (a question, discussion): do not decide; forward it as guidance only.
  2. Issue moved to Done with no user comment and no agent "Settled" comment: treat as keep. Canceled: treat as "drop the item"; do not decide, forward it and leave the queue pending.
  3. After a decision: reply 🤖 Recorded in the queue as <confirmed|overturned>: "<answer>". <n> jobs re-queued. and, if the issue is not Done, move it to Done. Overturned items that need follow-up work get a new issue in the right milestone.

Queue -> Linear

  • A pending item with no issue gets one (format above).
  • An item that is no longer pending (decided at the CLI, or mark_done) gets a 🤖 comment and moves to Done.
  • If an agent settled an item in Linear but the queue still says pending, run mark_done/decide for it rather than leaving the two out of step.

Notifying sessions

After applying or receiving anything, list sessions for this project (list_sessions, not archived) and send_message the ones that are active a short note: item id, the answer, whether it overturned the default, and the Linear URL. The decision itself is durable in queue.json; the runner re-queues jobs tagged with an overturned item, so a session that misses the message still picks it up from the queue.

State

work/linear-sync-state.json (untracked): {"seen_comments": [ids], "last_run": iso}. Never put secrets or game content in Linear or in this file.
