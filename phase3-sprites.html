Phase 3: Sprites

Rendered from docs/phase3-sprites.md, a working record of the project.

Results and decisions for Phase 3 (Linear milestone "Phase 3: Sprites"). The plan is the Linear document "Remaster plan"; this file holds the numbers. Earlier sprite work: bakeoff-results.md ("Sprite test", Phase 1b item 8), pack-archive.md (August sprites-lifelike*, October SR/contour trees), and the research notes sprite-consistency-research.md and face-detail-research.md in the coordinator's session notes.

Starting point (2026-11-22)

  • Pack: generated/playable-overrides-2x-remaster-it9 (Phase 2, 65 of 80 rooms redrawn). Shared and walk sprites come from enhanced/sprites-temporal (184 resources, one palette projection each); room objects and cAnims from work/assemble/backgrounds (37,493 frames under sprites/scene_NNN/).
  • Characters are the de-dithered SR sprites (LMY-42, provisional default sr-baseline).
  • Phase 1 sprite test (Holmes and Watson, frames 24-31, cast sheet passed in images): pose IoU 0.90-0.93, identity steady by eye, but texture crawl (temporal warp error, high-pass) is 2.8-3.2x the SR floor (Phase 1b measured 3.3-4.0 with the loop pair), against a gate of 1.5.

Walk data

Each hero has a .SEQ file in walk.lib (parsed by WalkSequence::load: 9-byte VGS name, flip byte, uint16 length, 4 skipped bytes, then frame bytes; 1-based frames, 196 means "range from the previous number to the next", 0 ends a run, 129/130 are control codes). SVGAWALK.SEQ and WATSON.SEQ have the same layout, 28 sequences:

Sequences Frames (0-based) What
0-4 0-11, 12-23, 24-35, 36-47, 48-59 five walk loops of 12 frames; 5-7 are 3-1 mirrored
8-12 60-66, 67-73, 74-80, 81-87, 88-94 five stop runs (6 frames + a held stand frame); 13-15 mirrored
16-27 other resources (TUPRIGHT, TRIGHT, TDOWNRG; Watson TW*) turns and talk poses

So each hero needs 95 frames redrawn in SVGAWALK/WATSON (10 cycles), plus the turn/talk resources. The Phase 1 frames 24-31 are two-thirds of walk loop 2 (24-35), which loops 35 -> 24 in game.

Bake-off pilot: keyframe + flow propagation (CPU, 0 server images)

On the existing Phase 1 redraws of frames 24-31, keys 24/26/28/30, flow (OpenCV DIS) on the de-dithered inputs, a confidence mask from the photometric residual of the warped input and forward-backward consistency, nearest key wins, low frequencies from the frame's own redraw. A throwaway reference implementation written to check the acceptance test (tools/tests/test_remaster_propagate.py); the real module is delegated (p3-1-propagate). Ratio = high-pass temporal warp error / SR floor, no loop pair:

Character, backend independent propagated (tol 12, fb 1.5) coverage propagated (tol 40, fb 8) coverage
Holmes 4B 3.19 2.81 0.08 1.71 0.64
Holmes 9B 2.84 2.50 0.08
Watson 4B 3.00 2.43 0.17
Watson 9B 2.99 2.52 0.18
  • With the strict mask only 8-20% of in-between pixels are propagated (legs and coat edges fail the flow check), so crawl drops only ~15%.
  • With every pixel propagated, the ratio is still 1.72, and the in-betweens tear (broken coat edges where the flow is wrong). The floor is not reachable this way because the keys themselves differ: each in-between matches its source key but jumps to the next key.
  • Sharpness is kept (0.96-0.99 of the independent redraw).

Conclusion: propagation is a building block, not the answer. The keys must be consistent with each other. Next candidates (need the server, so they wait for disk):

  1. Chained edit: redraw frame t with images = [original frame t, the previous redraw warped onto t, cast sheet], prompt to keep the fabric and folds of the second image. Walk the loop in order; close the loop by also checking 35 -> 24.
  2. Warped prior + low strength: img2img (strength ~0.45, the server field exists) on the warped previous redraw, so the model only repairs disocclusions.
  3. Propagation + low-strength cleanup of the in-betweens.
  4. Grid sheet of a whole loop with a cast cell (research note: identity steadier, pose worse).

Each is scored on full 12-frame loops with the loop pair, pose IoU, sharpness and identity drift.

Contour folders (LMY-56)

mods/rosetattoo-contour-candidate-20261031 and enhanced/*-contour-staging-20261031 are not needed by Phase 3. Nothing reads them (no tool, config or engine path); Phase 3 cuts alpha from the redrawn art; the sprite fallback is the SR baseline (enhanced/sprites, enhanced/sprites-temporal, the kept *-remaster-20261031 trees), and the staging trees are a deterministic alpha-only pass over those (refine_rosetattoo_sprite_alpha.py --method scale4-box --radius 0.35 --thin-guard --preserve-support), so they can be rebuilt. Keep palette-walk-remaster-20261031 and the other *-remaster-20261031 baselines.
